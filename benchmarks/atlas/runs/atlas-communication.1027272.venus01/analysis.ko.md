# Atlas V3 통신 전략 비교 결과

작업 `1027272.venus01`, 2026-10-24(싱가포르 시간), 노드 `cnode-33-43-32`. 전략 비교에는 이 작업 안에서 조건이 일치하는 구성의 시간만 사용한다.

## 검증 결론

- PBS와 스크립트의 종료 상태는 모두 0이며, 업로드한 소스 파일 27개의 체크섬 검사가 모두 통과했다.
- 정식 기록은 30건으로, 6개 구성 그룹마다 5회씩 실행했다. 원본 분할 파일과 병합 파일이 일치하며, CSV와 comparisons.json의 통계를 모두 독립적으로 재계산했다.
- 데이터 지문과 초기 중심이 이 작업의 V0 수치 참조와 일치하며, 모든 정식 실행의 최종 군집 개수는 동일하고 합계는 1000000이다.
- SSE 범위는 73440053.240119844675부터 73440053.240119844675까지이다. V0 대비 최대 절대 오차는 6.63102e-06, 스케일 조정 오차는 9.03e-14이다. 여기서 스케일 조정 오차는 절대 오차/max(1,abs(V0 SSE))이다.
- 선택한 소규모 데이터 구성의 중심, 레이블, 개수와 SSE 비교가 통과했다. 구체적인 오차는 preflight-check.json과 analysis.audit.json에 있다.
- rank 기록 120개와 정식 실행 시작 전 OpenMP 스레드 탐색 기록 360개를 확인했다. 같은 P/T의 두 전략과 모든 반복은 동일한 rank/스레드 코어 배치를 사용하며, 겹침이나 할당 범위 이탈이 없다.

## 환경과 비교 범위

GCC 9.2.0, Open MPI 4.1.2, Python 3.8.5, AMD EPYC 7R13 KVM 노드이다. N=1000000, D=32, K=32, seed=42로 고정하고, 워밍업 2회 뒤 초기 중심을 복원한 후 20회를 측정했다. 모든 구성은 P×T=12이며 단일 노드에서 실행했다.

구성별 성능 차이는 아래 표에 있다. 최소–최대 범위는 신뢰구간이 아니다.

## 성능 결과

시간은 kernel_seconds의 중앙값이다. 데이터 생성, 초기화, 워밍업, 최종 평가와 실행 시작 탐색은 커널 시간에 포함하지 않는다. 각 P/T 안에서는 두 전략을 교차 실행하고 매 라운드 순서를 무작위로 정했다. P/T별로는 블록 순서로 실행했으며 모든 구성을 전역적으로 교차 실행한 것은 아니다.

| P×T | Allreduce 중앙값/초 | 최소–최대/초 | Reduce+Bcast 중앙값/초 | 최소–최대/초 | 첫 전략 시간/둘째 전략 시간 | 둘째 전략 시간 감소 |
|---|---:|---:|---:|---:|---:|---:|
| 2×6 | 0.910166 | 0.906586–0.930287 | 0.913610 | 0.888920–0.947241 | 0.996× | -0.38% |
| 4×3 | 0.919556 | 0.916105–0.929694 | 0.935007 | 0.886339–0.949262 | 0.983× | -1.68% |
| 6×2 | 0.923267 | 0.889835–0.927843 | 0.922502 | 0.887874–0.927026 | 1.001× | 0.08% |

표의 “둘째 전략 시간 감소”가 음수이면 이번에 관측한 둘째 전략의 중앙 시간이 더 길다는 뜻이다.

동일 P/T에서는 통신 전략만 바꾸었으며, 차이를 판단할 때 반복 범위도 고려해야 한다. 현재 결과는 통신 단계만의 독립 비용을 직접 측정하지 않으므로 병목 분석에는 별도 프로파일링이 필요하다.

Allreduce 대비 Reduce+Bcast의 중앙 시간 변화는 2×6에서 +0.38%, 4×3에서 +1.68%, 6×2에서 -0.08%이다. 각 구성에서 두 그룹의 시간 범위가 모두 겹치므로 이번 결과만으로 한 통신 전략의 안정적인 성능 우위를 판단하기에는 근거가 부족하다. 기본 Allreduce를 유지할 수 있으나 이 선택을 성능 우위의 증명으로 설명해서는 안 된다. 이번에는 리덕션/브로드캐스트 단계를 따로 측정하지 않았으므로, 커널 총시간이 비슷하다는 이유로 통신 단계 자체의 시간이 같다고 추론할 수 없다.

이번 OS CPU 할당은 `60,61,62,63,64,65,66,67,68,69,70,71`이며 모두 socket 1을 사용한다. 측정한 구성의 소켓 간 rank는 `{"2": [], "4": [], "6": []}`이다. 따라서 “작업 전체가 소켓에 걸침”과 “개별 rank의 스레드가 소켓에 걸침”을 구분해야 하며, 비교하는 전략의 배치는 동일하게 유지했다.

이 비율은 고정 자원에서의 전략 비교이며 직렬 대비 강한 확장성 속도 향상이 아니다. 이 작업의 대규모 입력 V0는 수치 검증용으로 한 번만 실행했으므로 반복 시간 측정 성능 기준선으로 사용하지 않는다.

## 한계와 후속 작업

스레드 affinity는 알고리즘 실행 전 독립 OpenMP 탐색기로 얻었다. 이후 래퍼는 동일한 CPU mask와 환경으로 알고리즘을 실행하며, 알고리즘도 실제 스레드 팀 크기를 별도로 확인한다. 이 기록은 알고리즘 시간 측정 루프 안에서 스레드를 실시간으로 표본 추출한 것이 아니다.

서로 다른 작업은 노드, socket/NUMA 할당과 시스템 상태가 다를 수 있으므로 이번 V3 시간과 앞선 하이브리드 작업의 작은 차이를 최적화 이득으로 해석하지 않는다. 다른 작업의 V0 시간으로 이번 속도 향상을 계산하지 않았다.

결론은 현재 합성 데이터 규모, 노드 할당과 측정한 전략만 다룬다. 모든 원시 기록, 컴파일 로그와 배치 기록을 보존하며, HPC/analyze-atlas-strategy-results.py로 분석을 재계산할 수 있다. 주요 실험 데이터가 모두 모였으므로 도표와 보고서 정리에 들어갈 수 있다. 약한 확장성, 프로파일링과 다중 노드 실험은 보고서 필요에 따라 보충한다.
