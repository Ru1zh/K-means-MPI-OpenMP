# Atlas V3 단일 노드 프로세스 강한 확장성 결과

[English](analysis.md) | [简体中文](analysis.zh-CN.md) | [한국어](analysis.ko.md)

작업 `1027222.venus01`, 2026-10-24, 계산 노드 `cnode-33-43-39`. 분석에는 이 작업의 데이터만 사용하며 앞선 N=100000 파일럿과 합치지 않는다.

## 검증 결과

- PBS Exit_status=0, 스크립트 exit_status=0이다. 기록 35건이 모두 있으며, 7개 구성 그룹마다 5회씩 반복했고 누락이나 중복 번호가 없다.
- 원시 JSONL과 CSV의 중앙값, 최소값, 최대값이 그룹별로 일치한다.
- 모든 기록의 데이터 지문, 초기 중심 표본 번호, 최종 군집별 개수가 같고 개수의 합은 모두 1000000이다.
- SSE 범위는 73440053.240113213658부터 73440053.240119844675까지이며, 절대 폭은 6.63102e-06, 상대 폭은 9.03e-14이다. 독립 검증은 상대 허용 오차 1e-12를 통과했다.
- 이 작업에서는 전체 수치 단위 테스트를 다시 실행하지 않았다. 이전 validation 작업 1027219에서 테스트 12개가 통과했으며, 이번에는 대규모 입력 결과의 일관성 검사를 추가했다.
- 정식 MPI 실행 시작 30회의 rank 바인딩 보고서 140개가 모두 있으며 각 P의 사전 검사와 일치한다.

## 환경과 시간 정의

AMD EPYC 7R13, KVM 가상 머신이다. 노드에서 CPU 96개, 소켓 2개, NUMA 노드 4개, 코어당 하드웨어 스레드 1개가 보인다. 작업 할당은 12코어, 8 GB이며 walltime은 5분 11초였다.

GCC 9.2.0, Open MPI 4.1.2, Python 3.8.5를 사용했다. 빌드 옵션은 `-O3 -std=c++17 -Wall -Wextra -Wpedantic`이며 MPI 프로그램은 추가로 `-fopenmp -DKM_MPI`를 사용했다. 전체 컴파일 명령은 PBS 주 로그에 있다. Python 자체가 보고한 빌드 컴파일러 GCC 7.3.0은 이번 C++ 알고리즘이 그 버전을 사용했다는 뜻이 아니다.

N=1000000, D=32, K=32, seed=42로 고정하고, 워밍업 2회 뒤 초기 중심을 복원한 후 정식으로 20회를 측정했다. 각 그룹은 5회 반복하고 매 배치의 구성 순서를 섞었다. V3는 프로세스당 스레드 1개와 Allreduce 통신으로 고정했다. V1, V2나 다중 스레드 V3는 측정하지 않았다.

아래 표는 `kernel_seconds`의 중앙값을 사용하며, 이는 각 rank의 Lloyd 반복 소요 시간 중 최대값이다. 데이터 생성, 초기화, 워밍업, 최종 평가, MPI 실행 시작과 컴파일은 포함하지 않으므로 전체 작업 시간이나 종단 간 시간이라고 부르면 안 된다. 그룹별 총시간과 외부 실행 시작 시간의 중앙값은 analysis.audit.json에 별도로 저장했다.

V3의 12프로세스 중앙 시간은 0.949930초이며, V0 대비 11.824배, 효율 98.54%이다. 동일 V3 구현의 단일 프로세스 대비로는 11.545배, 효율 96.20%이다. 이 입력은 이번 단일 노드의 1–12프로세스 범위에서 선형에 가까운 확장성을 보인다.

단일 프로세스 V3의 중앙 시간은 V0보다 약 2.37% 낮다. 둘은 별도로 컴파일한 직렬 및 MPI/OpenMP 실행 파일이므로 V0 대비 속도비에는 이 차이가 포함된다. P=2,4,6에서 V0 대비 효율은 100%를 조금 넘고, 동일 구현 기준으로도 P=2,4는 100%를 조금 넘는다. 이는 원시 측정의 비율이므로 그대로 보존해야 한다. 캐시 작업 집합 변화, 컴파일 경로와 시스템 변동이 가능한 요인이지만, 이번에는 하드웨어 카운터를 측정하지 않아 인과관계를 확정할 수 없으며 초선형 이득이 안정적으로 성립한다고 주장해서도 안 된다.

## CPU 배치와 한계

PBS에서 사용 가능한 OS CPU는 `40-45,86-91`이다. V0는 taskset으로 CPU 40에 고정했고, 모든 P의 MPI rank 0 사전 검사도 CPU 40에서 실행했다. rank마다 코어 하나만 사용하며 겹침이나 초과 구독이 없다.

- P=1,2,3,4,6: CPU 40부터 순서대로 사용하며 모두 socket 0, NUMA node 1에 있다.
- P=12: rank 0–5는 CPU 40–45, rank 6–11은 CPU 86–91에 있다. socket 0/1과 NUMA node 1/3을 사용한다.

이번에는 개별 다중 스레드 rank가 소켓에 걸치는 경우가 없지만, P=12의 전체 배치는 두 소켓에 걸친다. 따라서 6프로세스와 12프로세스 비교에는 코어 증가, 캐시/메모리 자원 증가와 소켓 간 통신이 동시에 포함된다. NUMA 조건을 엄격히 고정한 실험으로 해석하거나 노드 간 실행으로 일반화할 수 없다.

실제 OS affinity는 정식 시간 측정 전에 독립 Python rank 탐색기로 검사했다. 정식 MPI 실행 시작 30회에서도 논리적 바인딩 보고서와 탐색 보고서의 일치를 추가 확인했다. 시간 측정 프로그램은 매 반복마다 sched_getaffinity를 표본 추출하지 않았다. 이 증거는 이번 매핑의 일관성을 뒷받침하지만 매 순간의 감시나 물리 하드웨어 독점 사용 보장은 아니다.

libbat.so, libosmcomp.so.3, libpsm_infinipath.so.1이 없다는 MPI 선택 구성요소 경고는 ignored로 표시되었으며 이번 실행을 막지 않았다. 다중 노드 네트워크 성능은 아직 검증하지 않았다.

## 보고서에 사용할 수 있는 서술

Atlas의 AMD EPYC 7R13 계산 노드 하나에서 N=1000000, D=32, K=32로 고정하고 워밍업 2회, 시간 측정 반복 20회, 구성당 5회 반복을 사용했다. 프로세스당 스레드 1개로 고정하고 V3는 Allreduce를 사용했다. V0의 커널 시간 중앙값은 11.232365초, V3의 12프로세스 결과는 0.949930초로, 직렬 대비 속도 향상 11.824배와 효율 98.54%에 해당한다. 단일 프로세스 V3를 기준으로 하면 속도 향상은 11.545배, 효율은 96.20%이다. 모든 실행은 동일한 데이터와 초기 중심을 사용했고 최종 군집 개수가 같으며 SSE 상대 폭은 1e-12 미만이었다. 12프로세스 구성은 두 소켓을, 나머지는 한 소켓을 사용했으므로 이 결과는 해당 노드 할당과 배치에서의 단일 노드 프로세스 강한 확장성을 설명한다.

## 후속 실험

다음에는 총 코어 수를 고정한 MPI+OpenMP 구성 실험을 우선 수행하고 각 rank의 코어 집합과 소켓을 명시적으로 기록한다. 이를 통해 과제의 하이브리드 병렬 부분을 보완할 수 있다. 이후 필요에 따라 V2/V3, 통신 방식과 약한 확장성을 각각 비교한다. 작은 우위는 변동 범위와 추가 반복을 함께 고려해 판단해야 한다.

현재 보고서는 하이브리드 스레드 확장성, 노드 간 확장성이나 통신 병목에 대한 결론을 제공하지 않는다. 검증을 위해 업로드 소스 패키지, 원시 결과, 컴파일 로그와 이 디렉터리의 analyze.py를 보존한다.
