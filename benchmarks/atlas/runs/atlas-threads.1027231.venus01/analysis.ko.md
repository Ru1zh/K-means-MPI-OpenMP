# Atlas V2/V3 스레드 누적 전략 비교 결과

[English](analysis.md) | [简体中文](analysis.zh-CN.md) | [한국어](analysis.ko.md)

작업 `1027231.venus01`, 2026-10-24, 노드 `cnode-33-43-39`. 전략 비교에는 이 작업 안에서 조건이 일치하는 구성의 시간만 사용한다.

## 검증 결론

- PBS와 스크립트의 종료 상태는 모두 0이며, 업로드한 소스 파일 27개의 체크섬 검사가 모두 통과했다.
- 정식 기록은 30건으로, 6개 구성 그룹마다 5회씩 실행했다. 원본 분할 파일과 병합 파일이 일치하며, CSV와 comparisons.json의 통계를 모두 독립적으로 재계산했다.
- 데이터 지문과 초기 중심이 이 작업의 V0 수치 참조와 일치하며, 모든 정식 실행의 최종 군집 개수는 동일하고 합계는 1000000이다.
- SSE 범위는 73440053.240119844675부터 73440053.240119874477까지이다. V0 대비 최대 절대 오차는 6.66082e-06, 스케일 조정 오차는 9.07e-14이다. 여기서 스케일 조정 오차는 절대 오차/max(1,abs(V0 SSE))이다.
- 소규모 데이터 6개 그룹의 중심, 레이블, 개수와 SSE 비교가 통과했다. 구체적인 오차는 preflight-check.json과 analysis.audit.json에 있다.
- rank 기록 120개와 정식 실행 시작 전 OpenMP 스레드 탐색 기록 360개를 확인했다. 같은 P/T의 두 전략과 모든 반복은 동일한 rank/스레드 코어 배치를 사용하며, 겹침이나 할당 범위 이탈이 없다.

## 환경과 비교 범위

GCC 9.2.0, Open MPI 4.1.2, Python 3.8.5, AMD EPYC 7R13 KVM 노드이다. N=1000000, D=32, K=32, seed=42로 고정하고, 워밍업 2회 뒤 초기 중심을 복원한 후 20회를 측정했다. 모든 구성은 P×T=12이며 단일 노드에서 실행했다.

3개 구성 모두에서 V3의 모든 실행은 대응하는 V2의 모든 실행보다 빨랐으며 시간 범위가 겹치지 않았다.

## 성능 결과

시간은 kernel_seconds의 중앙값이다. 데이터 생성, 초기화, 워밍업, 최종 평가와 실행 시작 탐색은 커널 시간에 포함하지 않는다. 각 P/T 안에서는 두 전략을 교차 실행하고 매 라운드 순서를 무작위로 정했다. P/T별로는 블록 순서로 실행했으며 모든 구성을 전역적으로 교차 실행한 것은 아니다.

| P×T | V2 원자적 갱신 중앙값/초 | 최소–최대/초 | V3 전용 버퍼 중앙값/초 | 최소–최대/초 | 첫 전략 시간/둘째 전략 시간 | 둘째 전략 시간 감소 |
|---|---:|---:|---:|---:|---:|---:|
| 2×6 | 1.501355 | 1.431110–1.544514 | 0.897849 | 0.862031–0.954998 | 1.672× | 40.20% |
| 4×3 | 1.373188 | 1.340761–1.394033 | 0.893993 | 0.872011–0.981837 | 1.536× | 34.90% |
| 6×2 | 1.155894 | 1.097906–1.196416 | 0.943962 | 0.920078–0.980020 | 1.225× | 18.33% |

V2/V3 중앙 시간비는 P=2, T=6에서 1.672배, P=4, T=3에서 1.536배, P=6, T=2에서 1.225배이다. 이번에 스레드 수가 많을수록 이득이 커진 경향은 전용 버퍼로 공유 원자적 갱신을 줄이려는 설계 의도와 일치한다.

프로세스 수도 함께 바뀌므로 데이터 분할, 통신과 캐시 조건도 달라진다. 이번에는 원자적 연산 대기 시간이나 하드웨어 카운터를 직접 기록하지 않았으므로 시간 차이 전체를 원자적 연산 경합 탓으로 정량적으로 돌릴 수 없다. 원인을 더 분해하려면 별도 프로파일링을 수행하고 진단 표본이 정식 시간에 섞이지 않도록 해야 한다.

이번 OS CPU 할당은 `40,41,42,43,44,45,86,87,88,89,90,91`이며 작업 전체는 socket 0,1을 사용한다. 측정한 구성의 소켓 간 rank는 `{"2": [], "4": [], "6": []}`이다. 따라서 “작업 전체가 소켓에 걸침”과 “개별 rank의 스레드가 소켓에 걸침”을 구분해야 하며, 비교하는 전략의 배치는 동일하게 유지했다.

이 비율은 고정 자원에서의 전략 비교이며 직렬 대비 강한 확장성 속도 향상이 아니다. 이 작업의 대규모 입력 V0는 수치 검증용으로 한 번만 실행했으므로 반복 시간 측정 성능 기준선으로 사용하지 않는다.

## 한계와 후속 작업

스레드 affinity는 알고리즘 실행 전 독립 OpenMP 탐색기로 얻었다. 이후 래퍼는 동일한 CPU mask와 환경으로 알고리즘을 실행하며, 알고리즘도 실제 스레드 팀 크기를 별도로 확인한다. 이 기록은 알고리즘 시간 측정 루프 안에서 스레드를 실시간으로 표본 추출한 것이 아니다.

서로 다른 작업은 노드, socket/NUMA 할당과 시스템 상태가 다를 수 있으므로 이번 V3 시간과 앞선 하이브리드 작업의 작은 차이를 최적화 이득으로 해석하지 않는다. 다른 작업의 V0 시간으로 이번 속도 향상을 계산하지 않았다.

결론은 현재 합성 데이터 규모, 노드 할당과 측정한 전략만 다룬다. 모든 원시 기록, 컴파일 로그와 배치 기록을 보존하며, HPC/analyze-atlas-strategy-results.py로 분석을 재계산할 수 있다. 다음에는 준비된 통신 방식 비교를 실행하고 동일한 대표 P/T 구성을 계속 유지할 수 있다.
