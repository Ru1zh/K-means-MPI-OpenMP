# Atlas 고정 12코어 MPI+OpenMP 구성 결과

작업 `1027229.venus01`, 2026-10-24, 노드 `cnode-33-43-45`. 이 분석은 동일 작업 안에서 12코어를 고정한 여섯 V3 구성만 비교한다.

## 검증 결론

- PBS와 스크립트의 종료 상태는 모두 0이다. 정식 기록 30건이 모두 있으며, 구성당 5회 반복하고 매 배치마다 여섯 구성을 모두 포함했다.
- CSV의 중앙값, 최소값과 최대값은 그룹별로 원시 JSONL과 일치한다.
- 모든 실행의 데이터 지문은 `7fcf2e8b0cc1a222`이며, 초기 중심 번호와 최종 군집별 개수가 완전히 같고 개수의 합은 1000000이다.
- 모든 정식 실행의 SSE는 73440053.24011984이다. 이번에는 대규모 입력 V0를 다시 측정하지 않았다. 여섯 구성의 소규모 데이터 결과는 별도로 직렬 참조와 비교했으며, 레이블/개수가 같고 중심과 SSE는 지정 허용 오차 이내였다. 구체적인 오차는 analysis.audit.json에 저장했다.
- 정식 실행 30회의 rank CPU mask 140개와 OpenMP 스레드 탐색 기록 360개를 확인했다. 모두 배치 계획과 일치하고 겹치지 않으며 할당된 12코어 전체를 사용한다. 원시 기록은 placement_id로 실제 실행 시작 디렉터리와 하나씩 연결된다.
- 모든 정식 실행의 MPI 실행 파일 SHA-256은 binaries.sha256과 일치한다. 탐색기의 `_OPENMP` 매크로는 201511이다. 이는 컴파일 시 OpenMP 표준 버전이며 런타임 라이브러리 배포 버전이 아니다.

## 하드웨어, 배치와 워크로드

AMD EPYC 7R13, KVM 가상 머신이다. CPU 96개, 소켓 2개, NUMA 노드 4개, 코어당 하드웨어 스레드 1개가 보인다. 작업은 12코어, 8GB를 요청했으며 walltime은 5분 43초였다.

이번 실제 할당은 OS CPU `36–47`이며 모두 socket 0, NUMA node 1에 속한다. 모든 구성은 동일한 서로 다른 물리 코어 12개를 사용하며, rank당 T개 코어를 받고 모든 cross_socket_ranks는 비어 있다. 따라서 앞서 예상했던 “1×12, 3×4가 소켓에 걸치는” 상황은 이번 할당에서 나타나지 않았다.

GCC 9.2.0, Open MPI 4.1.2, Python 3.8.5를 사용했으며, 알고리즘은 `-O3 -std=c++17 -Wall -Wextra -Wpedantic -fopenmp -DKM_MPI`로 컴파일했다. V3, Allreduce, N=1000000, D=32, K=32, seed=42로 고정하고, 워밍업 2회 뒤 초기 중심을 복원한 후 20회를 측정했다. 구성마다 5회 반복하고 각 배치의 순서를 무작위로 정했다.

실행을 시작할 때마다 Python 래퍼가 rank의 OS CPU mask, 명시적인 코어별 OMP_PLACES와 OMP_PROC_BIND=close를 설정한다. 독립 OpenMP 탐색 프로그램이 각 스레드가 지정된 코어 하나를 사용하는지 먼저 검사한 뒤 K-means를 실행한다. MPI의 `--bind-to none`은 MPI 실행기가 추가 바인딩을 하지 않는다는 뜻일 뿐, 래퍼가 바인딩하지 않는다는 뜻은 아니다. 스레드 기록은 독립 탐색 프로그램에서 얻고, 알고리즘 자체도 스레드 팀 크기를 별도로 확인한다. 알고리즘 시간 측정 루프 안에서 affinity를 실시간으로 표본 추출한 것은 아니다.

## 동일 작업 내 구성 비교

P는 MPI 프로세스 수, T는 프로세스당 스레드 수이며 모든 구성은 P×T=12이다. 시간은 kernel_seconds의 중앙값으로, 컴파일, 데이터 준비, 초기화, 워밍업, 최종 평가와 외부 실행 시작 비용을 제외한다. 최소–최대 범위는 실측 5회에서 얻었으며 신뢰구간이 아니다.

| P×T | 커널 시간 중앙값/초 | 최소–최대/초 | 12×1 시간/이 구성 시간 | 12×1 대비 시간 변화 |
|---|---:|---:|---:|---:|
| 1×12 | 0.954366 | 0.921613–1.019229 | 1.0023× | -0.23% |
| 2×6 | 0.979631 | 0.970431–0.997293 | 0.9764× | +2.42% |
| 3×4 | 0.952300 | 0.916632–0.974131 | 1.0044× | -0.44% |
| 4×3 | 0.980928 | 0.916852–0.994980 | 0.9751× | +2.55% |
| 6×2 | 0.984793 | 0.900327–0.988295 | 0.9713× | +2.96% |
| 12×1 | 0.956526 | 0.946156–1.003424 | 1.0000× | +0.00% |

이번 관측에서는 3×4의 중앙값이 가장 낮아 12×1보다 약 0.44% 낮았으며, 1×12는 12×1보다 약 0.23% 낮았다. 모든 중앙값은 0.952300–0.984793초에 있고, 최대/최소 중앙값 비는 약 1.0341이다.

여섯 그룹의 실측 최소–최대 범위에는 모두 공통 교집합이 있으며, 약 0.970431–0.974131초이다. 이는 정식 유의성 검정은 아니지만, 반복이 5회뿐이고 중앙값 차이가 매우 작다는 점을 함께 고려하면 이번 자료만으로 3×4를 안정적인 최적 구성으로 판단하기에는 부족하다. 더 적절한 결론은 이 입력과 동일 NUMA 노드의 12코어 할당에서 V3의 여섯 프로세스/스레드 구성이 비슷한 성능을 보인다는 것이다.

이 비율은 고정 자원에서 배치 차이를 나타내며, 코어 수 증가에 따른 강한 확장성 속도 향상이 아니다. 이를 다시 12로 나누어 병렬 효율로 사용해서도 안 된다.

## 이전 강한 확장성 작업과의 관계

이전 1027222는 cnode-33-43-39에서 실행했고 12프로세스가 두 소켓을 사용했다. 이번 노드는 cnode-33-43-45이며 12코어 모두 같은 소켓/NUMA 노드에 있다. 두 실행의 코어 바인딩 시작 방식도 다르다. 이전 V0=11.232365초를 그대로 적용해 “이번 직렬 대비 속도 향상”을 계산할 수 없으며, 두 작업 사이의 작은 시간 차이를 하이브리드 병렬화나 NUMA 최적화 때문이라고 해석할 수 없다.

## 보고서에 사용할 수 있는 서술

Atlas의 AMD EPYC 7R13 노드 하나에서 총 코어 수를 12로 고정하고 V3의 MPI/OpenMP 구성 1×12, 2×6, 3×4, 4×3, 6×2, 12×1을 비교했다. 모든 구성은 socket 0, NUMA node 1의 동일한 12코어를 사용했다. N=1000000, D=32, K=32로 고정하고 워밍업 2회, 시간 측정 20회, 구성당 5회 반복을 수행했다. 여섯 구성의 커널 시간 중앙값은 0.952–0.985초이며, 이번에는 3×4의 중앙값이 가장 낮아 12×1 대비 약 0.44% 감소했다. 반복 실행 범위가 겹치므로 이 구성이 안정적인 우위를 가진다고 판단할 수는 없다. 모든 실행의 데이터와 초기 중심이 같고 최종 군집 개수와 SSE가 동일하며, 여섯 구성의 소규모 데이터 비교도 직렬 참조 검증을 통과했다.

## 후속 비교 선택

준비된 스레드 전략 패키지와 통신 전략 패키지는 기본적으로 2×6, 4×3, 6×2를 사용하며 계속 사용할 수 있다. 이들은 서로 다른 스레드 수와 MPI 프로세스 수를 포괄하고, 이번 V3 실험에서 뚜렷한 성능 열세를 보이지 않았다. 이번 0.44% 차이만으로 하나의 “최적” 구성을 고르는 것보다 여러 대표 구성을 유지하는 편이 전략 비교에 적합하다.

다음에는 V2/V3를 먼저 실행해 원자적 갱신과 전용 버퍼의 차이를 살펴본 뒤 V3 Allreduce/Reduce+Bcast를 실행한다. 새 작업마다 실제 할당에 따라 배치를 계속 기록하고, 소켓 간 배치 조건이 달라지면 해당 결과에 설명해야 한다. 이번 결론은 측정한 단일 노드, 단일 입력 규모, Allreduce와 V3에만 적용되며, 다른 전략이나 다중 노드에서도 비슷하다는 것을 증명하지 않는다.

원본 파일은 그대로 유지한다. 같은 디렉터리의 analyze.py로 분석을 재계산할 수 있으며, 파일별 해시와 전체 파생 통계는 analysis.audit.json에 있다.
